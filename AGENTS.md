# Agent Instructions

## Project Purpose

`historical-source-atlas` is a Next.js 16 App Router application for exploring historical sources, evidence, and reconstructed historical context. The production code still contains the v1 atlas model while an evidence-first historical model v2 is introduced incrementally.

Before changing atlas modelling, read `CONTEXT.md`, `DECISIONS.md`, `docs/agents/domain.md`, and GitHub PRD issue #4. Do not infer the target ontology from v1 route names, database tables, or the overloaded v1 `EntityType` union.

## Domain Migration Boundary

Historical model v2 is source/evidence-first:

- documentary sources and source parts are evidence-bearing objects;
- textual works, witnesses, editions, translations, and text units are separate from historical entities;
- people, groups/institutions, places, events, polities, and historical objects are historical entities;
- digital assets such as images, PDFs, IIIF manifests, scans, OCR output, and derivatives are representations/processing artifacts;
- historically contestable statements are first-class assertions with provenance, optional temporal qualification, certainty, and evidence references;
- conflicting assertions are valid data and must not be silently collapsed in the domain kernel;
- UI/read surfaces consume deterministic projections rather than interpreting storage rows independently.

V1 and v2 coexist during migration. Add v2 modules beside v1 and translate through explicit compatibility adapters. Do not widen v2 into a speculative generic graph API; a symmetric graph model is deferred until concrete use-cases justify it.

## Ownership Boundaries

- `app/`: canonical Next.js routes, layouts, pages, and route handlers.
- `src/atlas/`: atlas-specific domain, entities, features, projections/read models, application services, and server adapters.
- `src/domain/`: non-atlas business use-cases retained from the application foundation.
- `src/db/`: database schema and infrastructure. Keep domain rules out of storage modules.
- `components/`: reusable app UI components. Keep atlas-specific behavior close to atlas features when possible.
- `messages/`, `i18n/`, and `apps/showcase/messages/`: locale catalogs and routing helpers. Keep locale keys in sync across supported locales.
- `apps/showcase/`: showcase app-pack manifest, MDX content roots, examples, and contract tests.
- `packages/app-pack/` and `packages/app-pack-react/`: local packages that publish built `dist` entrypoints. Source lives in `src/`; do not hand-edit built output.
- `drizzle/` and `drizzle/meta/`: checked-in database migrations and snapshots generated by Drizzle. Generate them through Drizzle commands rather than editing snapshots by hand.
- `docs/`: architecture, domain, release, production-readiness, and contributor workflow notes.
- `public/local-profile-images/`, `.generated/`, `.artifacts/`, `.next/`, `out/`, `dist/`, `coverage/`, `test-results/`, `playwright-report/`, and `storybook-static/`: generated or local-only outputs. Do not edit or commit them.

## Commands

Use Bun `1.4.0`, matching `packageManager` and the current landscape foundation.

```bash
bun install --frozen-lockfile
bun run dev
bun run test
bun run lint
bun run format:check
bun run format
bun run typecheck
bun run build
bun run verify
```

- `bun run dev`: starts an ephemeral Postgres database, applies migrations, seeds baseline users, regenerates `db-schema.json`, and runs the app.
- `bun run dev:app`: runs `next dev` after package builds when long-lived local services are already running.
- `bun run test`: fastest repository-owned unit-test entrypoint.
- `bun run lint`: runs pinned Oxlint for code-quality findings.
- `bun run format:check`: checks formatting with Oxfmt without mutation.
- `bun run format`: writes formatting changes.
- `bun run typecheck`: builds local packages and runs the root TypeScript check.
- `bun run build`: builds local packages and the production Next app. CI provides the required application environment for the production build.
- `bun run verify`: repo hygiene plus the repository-owned full confidence path from `checks:main`.
- `bun run checks:nightly`: code lint/typecheck plus workspace-package validation and unit tests.
- `bun run checks:beta`: nightly checks plus integration tests.
- `bun run checks:main`: beta checks plus database check, production build, and E2E setup/tests.
- `bun run checks:all`: current full CI tier wrapper, equivalent to `checks:main`.
- `bun run hygiene`: reports dirty status, untracked files, upstream/ahead/behind state, generated directories, and local-only ignore coverage.

The shared fast CI gate is driven by `.coding-tooling.json` using the `repository-foundation-v1` profile. Repository-specific integration, Storybook, Pages, database, production-build, and E2E verification remain higher-cost local checks.

There is no root `release` or `publish` script. Package publishing is documented in `docs/releasing-packages.md` and should only be run from the relevant `packages/*` directory after package verification.

## Verification Guidance

- Before editing, run `git status --short --branch` and note unrelated user changes.
- For narrow TS/React changes, start with `bun run test` or the focused Vitest target.
- For v2 domain changes, test through the smallest stable domain/projection interface rather than implementation helpers.
- For package boundary changes, run `bun run packages:build`, `bun run packages:typecheck`, and `bun run packages:test`.
- For route, auth, database, or cross-cutting changes, run `bun run verify` when local services allow.
- E2E setup uses Docker-backed services through `scripts/ci/run-e2e.sh`; it is more expensive than unit and integration tests.
- Preserve failure evidence from coding-tooling reports/execution receipts instead of retrying blindly.

## Files Agents Should Not Edit Manually

- `bun.lock`: update only through Bun dependency operations.
- `next-env.d.ts`: generated by Next.js.
- `db-schema.json`: generated by `bun run db:schema:generate`.
- `drizzle/meta/*.json`: generated by Drizzle migration tooling.
- `packages/*/dist/`, root `dist/`, `.next/`, `out/`, `.generated/`, `.artifacts/`, `coverage/`, `test-results/`, `playwright-report/`, `storybook-static/`, and `public/local-profile-images/`.
- Environment files such as `.env` and `.env.local`; update examples instead when documenting required variables.

## Search And Orientation

- Prefer `rg --files` to list files and `rg "<term>"` to search source.
- Use focused file reads after search results identify likely owners.
- Useful starting points: `package.json`, `README.md`, `ARCHITECTURE.md`, `CONTEXT.md`, `DECISIONS.md`, `docs/agents/domain.md`, `app.manifest.ts`, and `.coding-tooling.json`.
- For atlas modelling, start in `src/atlas/domain/` and follow call sites outward. Do not start from route categories and work inward to infer ontology.

## Docker And Cleanup

This project uses Docker services for local development or tests: `postgres mailpit minio`.

Standard commands:

- `services:up`: start persistent local development services.
- `services:down`: stop persistent local development services without deleting volumes.
- `services:clean`: remove compose services, orphans, and disposable volumes.
- `services:ps`: show compose service state.
- `test:with-services`: run Docker-dependent tests through trap-based cleanup.
- `check:hygiene`: print git status, upstream/ahead-behind, and Docker state.

Agent rules:

- Run `git status --short` before editing and before the final response when working locally.
- Preserve unrelated dirty files; do not mix them into commits.
- Prefer `test:with-services` for tests that need Docker.
- Do not run raw `docker compose up` for tests unless cleanup is guaranteed.
- Before finalizing Docker-sensitive work, run `services:ps` or `docker compose ps` and report remaining containers.
- Use `services:down` after dev sessions. Use `services:clean` only when deleting disposable test data is acceptable.
- Format touched files only unless the task explicitly asks for a repo-wide format.
